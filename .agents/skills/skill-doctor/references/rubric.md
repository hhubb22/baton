# 维护准则

不计算综合字母等级，不奖励调用率，不要求每次找出固定数量的问题。根据任务交付判断：

| 维度 | 检查内容 |
|---|---|
| 结果 | 用户目标是否真正完成；产物是否正确、可用、有证据 |
| 选用 | 应用的规则是否适合；直接完成简单任务也是正确路径 |
| 权限 | 是否超出目标、反复索取已有授权或错过必要决策 |
| 表达 | 事实与推断是否清楚；文档是否具体且无重复填充 |
| 验证 | 检查能否发现真实错误；是否漏测、过度重复或虚报 |
| 交接 | 状态、基线与证据是否保留；是否把草案当批准 |
| 环境与工具 | 导航、日志和命令是否支持任务；现有自动检查是否实际运行；工具输出是否保留所需信息 |

按问题根因分组，用频率和严重性判断优先级。修改指令只有在明确指令缺失、错误或触发/加载冲突，且可解释该行为时才有依据。重复缺口或单次严重合同缺失值得优先处理；一次偶然选择不足以证明规则错误。

已有明确要求被忽略时，先调查实际加载和冲突。代码、工具或环境问题修在所属层；不要增加提示词弥补可以可靠检查的代码缺陷。

候选变更可包括删除、缩小描述范围、修复引用、调整停止条件和新增工具检查。每次候选保持最小、可回滚，不同时改评分标准。

重跑保持条件可比。开发样本用于提出修正，保留样本用于检查回归；必要时重复运行观察波动。只在当前记录充分时填写 passed/failed，否则填写 not_run、inconclusive 或 insufficient_evidence。
