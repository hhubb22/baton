## Context

问题在于查询结果可能把配置当成当前设备状态。本示例不假定任何现有函数或 SDK 能力，真正实施前需定位规则配置来源、实际读取接口及错误表达。

## Proposed changes

拟在查询结果中分别表达 configured_action 与 observed_action。observed_action 是带状态的读取结果，区分已读值、不支持和读取失败；时间与读取结果绑定。不要用默认动作填充未知值。

与复用一个 action 字段相比，分开表达会增加响应字段和调用方处理，但能够避免语义混淆。是否需要兼容旧调用方必须先调查，不能假定能直接替换协议。

状态类型和响应字段是拟议设计，不是仓库现状。平台能力验证与接口兼容性决策阻塞正式编码，不阻塞制作隔离的响应格式示例。

## Testing and validation

| Requirement | Setup and observation | Failure condition | Status |
|---|---|---|---|
| R-01 | 配置返回 trap，模拟读取返回 drop，观察输出 | 输出合并或替换了其中一个值 | planned |
| R-02 | 分别模拟不支持与读取异常 | 输出实际动作却没有真实读取值，或丢失失败原因 | planned |
| R-03 | 先成功再失败，观察时间和状态 | 第二次失败仍被表现成新的成功读取 | planned |

模拟只验证结果表达，不能证明真实设备读取正确；设备实验计划需待平台能力确认后补充。
