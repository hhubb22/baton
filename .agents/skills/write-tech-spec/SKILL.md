# Write tech spec

交付可评审的设计，说明相对现状改变什么、为什么，以及如何验证。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。写作按需读取 [约定](references/technical-writing.md)；新文档使用 [模板](assets/TECH.template.md)，粒度参考 [示例](references/example-tech.md)。

## 调查后设计

先读取已有的行为依据与受影响代码，确定入口、状态所有者、调用关系和关键约束，调查范围限于相关区域。重要证据记录文件、符号和调查时的 commit；外部标准记录版本与条款。无法确认的事实保留为未知。

已有需求足够明确时可以不写 PRODUCT；局部明确的修改可以不写 TECH。确实需要实验才能决定时，优先提出或执行已授权的隔离原型；没有运行条件时，交付标明缺口的草案。

沿用项目路径；没有约定时保存为 `specs/<特性>/TECH.md`，与行为规格使用同一目录，并与实现代码在同一提交或 MR 中交付。

## 内容

Context 只描述决定本次设计的现状和约束。Proposed changes 解释进程或模块职责、接口、数据流、状态与所有权如何改变；按实际风险说明取消、失败、清理、兼容性和恢复。

用具体场景论证真实取舍，包括不做的后果；没有合理的替代方案时直接说明。行为要求通过 R 编号或明确段落引用。评审文档中有进程或模块级的需求条目时（例如 TR2 的 AR），设计条目标注所属条目；设计比条目更细是正常的，新增或冲突的部分按行为规格中的同样规则回报。重大而持久的选择可以建议提取 ADR，默认仍是提案。

Testing and validation 把关键要求对应到具体测试、实验或隔离环境步骤。写清设置、观察与失败条件，区分计划执行和已经执行；需要隔离环境的项目可以直接作为 `lab-request` 的输入，硬件或环境覆盖缺口显式列出。临时分工、分支和子 Agent 配置留在过程区。

## 交付

给出设计、关键证据、代价和未决问题；批准状态由用户确认。只有当前请求已经包含实施授权，且所需的重大决定已经明确时，才继续实施。

实现阶段改变模块边界或约定时，提交设计修订；纯定位信息和已确认的事实可以直接同步修正。保持设计理由与实际交付一致，行为契约的修改需要用户确认。
