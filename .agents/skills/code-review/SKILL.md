# Code review

审查真实差异，分别检查工程正确性与需求符合性。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。基线不明确或有工作区修改时阅读 [范围规则](references/diff-scope.md)；输出参考 [发现标准](references/findings.md)。

## 确定范围

优先使用用户指定的提交、分支、MR 或工作区，获取对应差异、提交清单和相关上下文。提交区间、暂存区、工作区和未跟踪文件分别确认，命令与覆盖范围按范围规则处理。报告中写明实际覆盖了哪些部分。

读取已有的项目审查规则，例如 REVIEW_GUIDE.md，以及差异涉及的规格、评审文档条目或接口契约，文档名称以项目为准。没有规格时照常检查正确性，并把需求符合性标为"依据受限"，只依据已知需求判断。

## 两条检查路径

工程路径关注会造成实际影响的问题：生命周期、并发、错误处理、兼容性、资源泄漏及项目约束。格式问题交给格式检查器；重构建议只在与本次改动直接相关时提出。

需求路径检查遗漏、错误实现、越界行为和验证缺口。规格与代码冲突时核查证据，由证据判断哪一方需要修改。

复杂差异可以把两条路径分开并行审查；小差异在同一会话中检查即可。合并结果时核验、去重，保留类别与证据。发现的数量以实际为准。

## 交付

每项发现写明位置、触发条件、影响、依据和严重性。区分可证实的缺陷、待确认的风险与非阻塞建议；缺少测试单独列为验证缺口。没有发现时，说明检查范围及局限。

只交付审查报告，代码和 MR 状态保持原样。用户明确要求修复时，把需要修复的发现作为输入交给 `implement-specs`，由它修改和验证；修复后可以再审查一次。
