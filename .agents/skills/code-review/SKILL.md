# Code Review — 代码审查

## Goal

针对真实代码差异（diff），从工程正确性、架构卫生与需求符合性三个维度输出有直接依据的审查发现。范围规则见 [diff-scope.md](references/diff-scope.md)，发现分级见 [findings.md](references/findings.md)，通用红线见 [operating-contract.md](references/operating-contract.md)。

## Workflow

1. **确认审查范围与依据**：
   - 获取目标 commit、分支或工作区的真实 diff，并读取关联规格（`PRODUCT.md` / `TECH.md`）或工单验收条件。
2. **三维检查**：
   - **工程正确性**：并发/锁顺序、事务与错误处理、资源释放、权限与安全边界、兼容性。
   - **需求符合性**：是否遗漏验收条件、越界修改无关模块或缺少关键路径验证。
   - **代码与文档卫生（防熵增检查）**：
     - 生产代码是否混入了 `BATON_TEST_*` 等测试专用环境变量钩子？
     - 长期文档（`README.md`、`TECH.md`）是否被追加了「当前已实现 PS-xxx...」之类的工单流水账？
     - 测试是否符合测试金字塔（能用单测覆盖的是否堆砌了脆弱的重型 E2E）？
3. **输出结构化审查报告**：
   - 每条发现写明：`[严重级别] 文件:行号 — 触发条件、实际影响与修复建议`。无问题时明确写「未发现阻塞问题」并说明已检查范围。

## Guardrails

- 只报告有代码或规格依据的真实问题，不湊数，不挑剔格式化器能处理的纯排版问题。
- 审查阶段默认只读，不直接修改业务代码或自动关闭工单。

## Stop Rules

- 输出审查报告后停下；仅在用户明确要求修复审查发现时，转入 `implement-specs` 进行修复。
