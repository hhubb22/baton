# To tasks

把工作切成可以独立验证的纵向切片，让每次会话只处理一个任务。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。清单使用 [模板](assets/TASKS.template.md)。

## 收集输入

- 输入是已确认的对齐结果、行为规格、技术设计，或评审文档中已编号的需求条目（例如 TR 的 AR）。
- 有上游需求条目时以它为起点：一条可以成为一个任务，也可以合并或拆分，任务注明所属条目。
- 读取受影响模块的代码，找出值得先做的预重构：先让改动变容易，再做容易的改动。

## 切分规则

- **纵向切片**：一个任务打通一条完整路径，例如 Web 服务的 API → 业务逻辑 → 存储 → 响应，或网络设备的配置 → 控制面 → 芯片 → show 输出。完成后可以单独演示或验证。
- **大小**：一个新会话能够完成。
- **依赖**：写明每个任务被哪些任务阻塞；没有阻塞的任务可以立即开始。
- **验证方式**：单元测试、集成测试或回放、隔离环境验证，可以组合。需要隔离环境的任务单独标注，并尽量集中安排，减少往返。
- **顺序**：预重构排在最前。
- **宽范围机械改动**，例如重命名、修改共享类型：按 expand–contract 拆分。先新增新形式，再分批迁移调用方，每批一个任务，最后删除旧形式。

## 确认

用编号列表展示每个任务的标题、所属需求条目、阻塞于、交付什么、验证方式。

只要求拆分时，请用户确认粒度、依赖，以及是否需要合并或拆分，按反馈调整。当前请求已经授权继续实施时，保存清单后直接交给实施环节，不再等待确认；拆分中出现会改变范围或重要行为的取舍时，才停下来确认。

## 输出

写入过程区的 `TASKS.md`。任务清单只存在于过程区。

- 任务描述写行为，不写具体文件路径和代码片段，因为它们很快会过时。原型确定的关键数据结构可以内联，并注明来源。
- 标出依赖前沿：阻塞项全部完成、可以开始的任务。
- 状态取值：待开始、进行中、完成、搁置。搁置时写明原因。

交付任务清单的位置、可以立即开始的任务，以及需要隔离环境验证的任务汇总。
