# Domain modeling

让项目已有概念准确、一致，保留项目自己的词汇体系。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。整理词汇时使用 [格式](assets/GLOSSARY.template.md)；确有重要选择时使用 [ADR 模板](assets/ADR.template.md)。

## 对齐概念

优先读取项目配置指定的术语表，否则查找 GLOSSARY.md，并兼容已有 DOMAIN.md、CONTEXT.md 或其他词汇表。多模块项目只读取相关术语表。日常使用已有词汇时不需要启动本 skill。

比较当前定义、代码用法、标准或 SDK 术语与用户语境。指出冲突，并用具体的边界场景检验概念关系。能从代码查明的事实自行核查；需要选择语义时，给出候选及各自的影响。

保留项目推荐名称、标准名称和代码中的历史别名。重命名代码或修改接口需要已获准的迁移计划。标准术语引用标准定义，只记录项目中的特殊用法与差异。

## 写入与决策

用户要求维护文档时，可以写有依据的事实和草案。新的正式语义、词汇变更和重要架构选择，先获得明确确认；提议在确认前保持 proposed 状态。

词汇表只描述概念及其关系，实现过程、待办和模块架构放在各自的文档中。有实际内容时才创建文件；没有约定时默认 GLOSSARY.md，与代码一起提交。已有同类文档时更新它，避免创建同义副本。

用户要求把已有词汇表迁移为 GLOSSARY.md 时，保留内容、核对目标文件是否存在，并同步项目配置及依赖引用。目标已有不同内容时先核对冲突。迁移后检查所有受影响引用仍能找到术语；文件名变更不改变已确认的定义。

对跨版本仍有意义、存在真实取舍、未来读者需要理由的重要选择，建议记录 ADR；高风险政策也可以记录。保留 proposed、accepted、superseded 等状态和相互引用。

交付更新内容、依据和待确认的语义。实施和重构由后续任务单独发起。
