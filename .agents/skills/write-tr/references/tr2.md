# TR2 特性设计说明书：字段指南

标题：`<PICOS XX版本> <IR XX需求> TR2 特性设计说明书`

按下列顺序输出章节。输入为 TR1 快照中的 SR 列表。

## 1. 简介

特性规格范围及操作场景定义：简要回顾 TR1；TR1 链接写 `【待填：TR1 飞书链接】`；列出作为设计输入的 SR 列表（取自 TR1 快照，不改编号）。

## 2. 特性概述（起草）

| 小节 | 要点 |
|---|---|
| 特性需求原理 | 基本实现原理，引用标准条款 |
| 设计约束 | 例如：FRR 作为开源软件，尽量减少对 FRR 的修改 |
| 假设和依赖关系 | 依赖的芯片能力、内核特性、SDK 接口。尚未提供的依赖明确写出，并说明它阻塞哪些 SR/AR |

## 3. 特性设计

### 3.1 现有架构描述及架构设计备选（起草）

- 现有架构：特性涉及的 0 层架构，即相关进程、各进程定位和进程间关系。依据代码，引用路径。
- 备选方案：方案描述、架构变更项（新增进程/线程/LIB、新增连接）、优缺点。只写真实可行的方案。
- 最终方案：写建议和理由；专家裁决保留 `【待填：评审裁决】`。
- 遗留设计缺陷及规避措施。

### 3.2 主要逻辑数据和关键处理流程（起草）

- 关键逻辑数据：各进程保存的数据对象、关键 key、保存方式（树、链表、DB 等）。
- 主要处理流程：以进程为最小粒度，用 Mermaid 时序图表示。后续 SR 设计可以直接引用这里的流程。

### 3.3 功能需求设计（起草）

每条 SR 一节：

- **SR 设计**：引用 SR 描述；用时序图说明一个外部输入在设备内各进程间如何处理，写明各进程的输入、关键处理和输出。重点检查功能分配是否符合进程原有定位，以及进程间通信接口有何变化。
- **AR 分解**：AR 描述进程黑盒行为，编码 `AR.<SR编码>.<进程缩写>.<NNN>`。单进程处理的 SR 可直接分解 AR，不画时序图；涉及多进程交互的 SR 必须先做 SR 设计。

### 3.4–3.8 其余需求设计（起草）

故障、性能、可维护性、网管、可测试性需求设计，格式与 3.3 相同，覆盖 TR1 中对应分类的全部 SR。

## 4. AR 分解汇总（起草）

| AR 编码 | 所属 SR | 进程 | 描述 |
|---|---|---|---|

后续编码以本表为基础。拆分开发任务时，以 AR 为单位。

## 5. 接口定义（起草）

四类接口分别写变更前和变更后，对每个参数和字段写明含义、数据类型、取值范围：

- 进程间接口变更
- 进程与内核间接口
- 进程与硬件 SDK API 接口
- 共享 LIB 对外 API 接口

接口尚未由其他团队提供时（例如 SDK 侧接口），写明期望的接口语义，并标注 `【待确认：<提供方>】`。
