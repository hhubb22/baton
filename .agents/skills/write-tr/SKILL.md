# Write TR

产出可直接粘贴到飞书的 TR 草稿（Markdown），让评审者看清要做什么、为什么、如何验证。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。

TR 是评审时点的快照，通常早于实际开发，开发中会发生变动，TR2、TR3 尤其如此。因此两边分工如下：

- 开发开始前，TR 是写规格的输入：`write-product-spec`、`write-tech-spec` 依据它的 SR/AR 编写 PRODUCT.md / TECH.md。
- 开发开始后，仓库中的工程文档随代码演进，是权威来源。TR 保持基线不变，偏离通过"基线后变更记录"说明。
- 工程文档比 SR/AR 更细是正常的：PRODUCT.md 中的 R 条目标注所属 SR，TECH.md 中的设计条目标注所属 AR，偏离时按编号对应。

## 写到什么深度

按评审时已经确定的程度写，不为填满模板而补细节：

- 已决定的：写成结论，附依据。
- 倾向但未定的：写成拟议方案，并说明取决于什么。
- 要到开发中才能确定的：写 `【开发中确定：<取决于什么>】`。这比编造一个看似完整的设计更有用。

当前若已有原型或代码，以实际实现为依据起草，并注明哪些部分已验证。

## 选择阶段

| 阶段 | 字段指南 | 主要输入 | 对应工程文档 |
|---|---|---|---|
| TR1 场景分析 | [tr1.md](references/tr1.md) | 需求对齐结果、调查结论、现有代码 | PRODUCT.md |
| TR2 特性设计 | [tr2.md](references/tr2.md) | TR1 的 SR 列表、TECH.md、代码 | TECH.md（进程层） |
| TR3 概要设计 | [tr3.md](references/tr3.md) | TR2 的 AR 列表、TECH.md、代码 | TECH.md（模块层）与测试 |

用户未指明阶段时，根据已有材料判断，并在开头用一句话说明判断依据。只读取所选阶段的字段指南。

## 收集输入

1. 读取过程区（见任务边界中的文件位置）和仓库中该特性的 PRODUCT.md / TECH.md。
2. 上一阶段 TR 由用户从飞书导出后粘贴，保存为过程区的 `TR<n>.md` 快照，并记下其基线日期。
3. 产品现状、接口和数据结构以代码为准，引用路径、符号和调查时的 commit。
4. 标准条款以标准原文为准，记录标准名称、版本和条款号。

某项输入缺失时，只把依赖它的章节写成待填，其余章节照常起草。

## 字段归属

每个章节属于以下三类之一，字段指南逐节标注：

- **起草**：有代码、标准或工程文档作为依据。按依据写，并标注出处。
- **起草·需外部资料**：友商与竞品分析。仅在能访问官方文档时起草，每条附链接、产品型号和版本；截图和测试报告由用户补充。
- **人填**：需求提出人、客户信息与合同金额、客户期望时间、需求价值与澄清结论、产品形态勾选、工作量、评审裁决、评审问题、基线时间。这些字段保留占位符 `【待填：<内容>】`，交由用户填写。上下文中出现线索时，可以把线索写在占位符里供参考，但不写成结论。

## 编号

项目配置中写明的编号规则优先；没有写明时，SR 与 AR 编号使用模板规则；仓库中的 PRODUCT.md / TECH.md 用这些编号标注追溯关系：

- SR：`SR.<IR编码>.<分类>.<NNN>`，分类取 FUNC、PERF、DFX、NM、TEST、SEC。
- AR：`AR.<SR编码>.<进程缩写>.<NNN>`。

IR 编码由用户提供，未提供前用 `【待填：IR编码】` 占位，提供后统一替换。进程缩写没有统一约定：直接用进程的实际名称，过长时取能一眼认出的简称，同一特性内保持一致。已发布的编号保持不变；废弃的条目保留编号并注明原因。

## 写作

- SR 描述网元黑盒行为：输入、网元行为、输出。AR 描述进程黑盒行为。实现细节放在 TR2/TR3 的设计章节。
- 新增或变更 CLI 时，写全模板要求的项：作用、默认行为、关键字、参数范围、报错提示、互斥关系、产品形态裁剪；变更已有 CLI 时写清前后差异与兼容方式。CLI 按特性语义设计，与芯片能力解耦。
- 一条一句，一句一事，写明主语。先写结论，再写依据。
- 时序图、状态图和拓扑图用 Mermaid 编写，飞书可以直接渲染。
- 模板中的斜体说明是填写指引，产出时删除。可选章节不适用时，写"不涉及"加一句原因。
- 导出模板中的飞书图片链接带临时授权码，产出中不保留。

## 评审后

用户粘贴评审意见后，产出两样东西：

- **评审结论清单**：保存为过程区的 `TR<n>-review.md`，每条写明结论、涉及的 SR/AR、影响 PRODUCT 还是 TECH。工程文档由 `write-product-spec`、`write-tech-spec` 以这份清单为输入更新；本 skill 只读取工程文档。
- **评审问题跟踪**：在 TR 草稿的对应章节逐条列出问题和闭环状态。

| # | 结论 | 涉及 SR/AR | 影响文档 |
|---|---|---|---|
| C1 | … | … | PRODUCT / TECH / 无 |

## 基线后

- 工程文档在基线之后发生变化时，例如标注为"新增"的 R 条目或与 AR 不一致的设计，生成"基线后变更记录"条目：日期、涉及的 SR/AR、变更内容、原因，供用户贴回飞书。只记录影响行为、接口、范围或风险的变化，实现细节的调整不必回报。
- 不重写已基线的 TR 正文。

## 交付

把草稿保存为过程区的 `TR<n>-<特性>.md`，评审结论清单保存为 `TR<n>-review.md`，并报告三件事：已起草的章节、待填字段清单、依据不足的结论。飞书文档由用户自行更新；TR 草稿不提交到仓库。

交付前逐项核对：

```
- [ ] 章节标题与模板一致，顺序未变
- [ ] 每条 SR/AR 有编号，SR 汇总与 AR 汇总和正文一致
- [ ] 必选场景（功能、故障、可维护）均已覆盖；CLI 有变更时含网管场景
- [ ] 人填字段全部保留占位符，未写成结论
- [ ] 产品现状、接口、标准的结论都有出处
- [ ] 斜体指引和飞书图片链接已删除
```
