# Diagnose bugs

用可重复的信号定位根因。读代码猜原因很容易把第一个看似合理的解释当成结论，反馈回路是防止这种情况的主要手段。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。构造回路时参考 [回路清单](references/feedback-loops.md)。

复制下面的清单，逐项推进：

```
- [ ] 1. 反馈回路：能稳定复现症状的命令或步骤；暂时无法运行时，整理现有材料
- [ ] 2. 复现并最小化（有回路时）
- [ ] 3. 候选解释，以及区分它们的检查
- [ ] 4. 验证解释，定位根因
- [ ] 5. 回归测试与修复
- [ ] 6. 清理与报告
```

## 1. 建立反馈回路

先尽力建立回路，这是最值得投入的一步。回路满足四个条件才算可用：

- **能变红**：走真实的出错路径，断言用户描述的那个症状，而不是"没有崩溃"。
- **稳定**：每次运行结论相同。偶发问题要把复现率提高到可调试的程度，例如循环触发、加压、收窄时间窗口。
- **快速**：秒级优于分钟级。
- **可执行**：Agent 能直接运行；只能在开发环境无法直达的环境中复现时，用 `lab-request` 写需求单，由用户带回结果。

看到失败输出后进入第 2 步。

暂时无法运行时，不必停下：只有日志、core dump 或现场描述的问题很常见。这时基于现有材料调查，列出已经尝试过的回路，进入第 3 步。在拿到运行结果之前，所有结论都标为"未确认"。

## 2. 复现并最小化

- 确认复现的是用户描述的症状，而不是附近另一个问题。
- 一次删一个输入、配置或步骤，每次删除后重跑回路，只保留去掉就不再复现的部分。最小复现会成为回归测试。

## 3. 候选解释

写出有证据支持、可以证伪的候选解释，格式是："如果原因是 X，那么改变 Y 会让问题消失。"写不出预测的解释，要么具体化，要么放弃。

存在合理的替代解释时，全部列出并排序，再设计能区分它们的检查。证据已经明确指向一个原因时，写一个即可，同时说明其他可能为什么被排除。

开始验证前，把列表给用户看一眼：用户常有领域知识能立刻调整排序。用户暂时不在时，按自己的判断继续。

没有回路的情况下，交付候选解释、支撑它们的证据，以及能区分它们的下一项检查或需要的材料。

## 4. 验证与定位

- 每个探针对应一个解释的预测，一次只改一个变量。
- 优先用调试器；其次在能区分解释的边界处加日志。
- 调试日志统一加前缀，例如 `[DBG-a4f2]`，方便最后清理。
- 性能问题先测基线，再二分定位。

## 5. 修复与回归测试

在合适的接缝处，先把最小复现写成失败的测试，再修复，看它通过，最后用第 1 步的原始回路复验。

找不到合适的接缝本身就是一个发现：说明当前结构无法锁住这个缺陷。在报告中写明。

没有回路时，修复也标为"未验证"，并写明需要什么环境或材料来验证。

## 6. 清理与报告

- 原始回路不再复现；回归测试通过，或说明无法添加的原因。
- 删除所有带前缀的调试日志和一次性原型。
- 日志、抓包和输出中的密钥、口令和令牌一律脱敏。
- 报告根因及其验证状态、被证实的解释、修复内容和验证结果，写进提交说明，供下一个排查者参考。
