# 反馈回路清单

先看通用回路，再看与项目类型对应的一节。优先选能在开发环境运行的回路；必须进入隔离环境时再用需求单。

## 通用

1. **失败测试**：在能触达缺陷的最浅接缝处写测试，可以是单元、集成或端到端测试。
2. **命令行加固定输入**：用固定配置或输入运行程序，与已知正确的输出快照对比。
3. **回放**：把真实的请求、报文或事件序列保存到文件，单独送入出错的代码路径。
4. **最小化运行环境**：只启动相关的进程或服务，依赖用桩替代，一次函数调用就能走到出错路径。
5. **差分比较**：同一输入分别跑旧版本和新版本，或两种配置、两种实现，对比输出。
6. **二分**：问题出现在两个已知版本之间时，脚本化"构建 → 检查"，再用 `git bisect run`。
7. **随机输入**：偶发的错误输出用大量随机输入循环触发，寻找规律。

## 服务端与前端

- **HTTP 脚本**：用 curl 或小脚本请求本地服务，断言状态码和响应内容。
- **浏览器自动化**：用 Playwright 等工具驱动页面，断言 DOM、控制台和网络请求。
- **数据库状态**：准备固定的测试数据，执行后检查数据变化。

## 网络设备

- **协议栈替身**：用 Linux 内核实现或 veth 对代替设备端口，在开发机上运行协议进程。
- **报文回放**：把 pcap 中的报文送入解析或处理路径。
- **软硬件差分**：同一输入分别走软件实现和芯片实现，对比结果。
- **设备脚本**：在设备上执行配置与 show 命令，比较输出与预期；开发环境无法直连时通过 `lab-request` 执行。
- **计数器与跟踪**：芯片或 SDK 计数器、调试跟踪，加上时间戳。
- **直连拓扑**：互通、协商、故障恢复类问题，在两台设备的直连拓扑上复现。

## 偶发问题

目标是提高复现率，而不是追求一次干净的复现。循环触发上百次、并发、加压、收窄时间窗口。复现率达到能区分假设的程度，即可进入第 3 步。

## 现场材料

无法复现时向用户索取，并说明需要哪一段：

- 日志：注明进程或服务，以及时间范围。
- 请求记录或抓包：注明采集位置和时间范围。
- 运行配置或环境信息：注明机器或设备、版本和采集时间。
- core dump：附上对应的二进制和符号文件版本。

所有材料先脱敏再引用。
