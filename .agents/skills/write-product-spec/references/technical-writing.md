# 技术写作约定

写给会阅读代码的工程师。先用具体场景解释变化，再给精确行为或设计。段落负责论证，编号用于需要引用的要求，表格用于状态、字段或真实方案比较。只在图能更清楚表达关键关系时画图。

优先使用明确主语、主动语态和直接动词，写清谁在什么条件下做什么。删除不增加信息的开场预告、过渡语和名词化表达。一个句子集中表达一个主要意思，必要时拆句，但不为追求短句割裂因果关系。先给读者当前需要的结论或问题，再补背景、理由和证据。

以下默认值参考简化技术英语（ASD-STE100）的做法，数字是本库为中文换算的经验值，不是标准：

- 一句约 40 个汉字以内；操作步骤一句一个动作。
- 一段约 6 句以内，围绕一个论点。
- 修饰链不超过三层，例如写"XPN 协商失败时的告警"，不写"MKA XPN 密码套件协商失败处理告警机制"。
- 一个术语只表达一个意思；同一概念全文用同一个词。

超出默认值时先检查能否拆分；确实需要保留因果关系的长句可以保留。

现状引用实际代码、测试或标准，关键引用记录调查版本。代码符号与路径帮助定位；行号说明以调查 commit 为准。新设计用拟议语气，验证结果必须来自实际执行。证据缺口写成未决问题，不能用想象的文件、测试结果或批准人填空。

每个结论提供会改变判断的信息：具体行为、依据、约束、取舍或验证。将“可靠、高性能、优雅、可扩展”等愿望变成条件和可观察结果。没有指标时提出待确认预算，不编造数值。

每项信息只保留一个权威位置。行为规格描述使用方契约；技术设计引用要求并解释实现；ADR 记录重大选择；进度和子 Agent 分工留在临时计划。沿用已有文件与术语，不强制改名。

采用模板的核心信息结构；无信息的可选章节直接省略。使用真实候选方案解释利弊，不凑数量，不重复摘要、目标、收益和总结。示例只示范表达，不是当前项目的事实来源。

文档默认草案。用户对方案的确认不等于全部未决问题获准，也不等于全部发布动作获准。实现中发现偏差先判断是缺陷还是需要修订设计，不能把要求改弱来迁就代码。
