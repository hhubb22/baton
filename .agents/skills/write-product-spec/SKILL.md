# Write product spec

交付使用方能够理解和检验的行为约定。使用方可以是人、API 调用者、协议对端或其他模块。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。写文档时按需读取 [写作约定](references/technical-writing.md)；新文档采用 [模板](assets/PRODUCT.template.md)，需要校准粒度时看 [示例](references/example-product.md)。

## 依据与范围

先利用过程区的对齐结果、外部评审文档快照、已确认的决定和项目已有规格。只有会改变本阶段行为的缺口才提问；代码和环境事实自行核查。UI 工作优先使用已有设计稿。

修订现有文件优先于创建副本。没有路径约定时使用 `specs/<特性>/PRODUCT.md`，与实现代码在同一提交或 MR 中交付。

## 写出行为

用简短场景解释动机与使用方式，再用稳定的 `R-01` 等编号描述关键要求。写清条件、动作与可观察的结果，覆盖本次变化涉及的正常、错误、取消、重试或并发情形。只保留与风险有关的情形。

有外部评审文档或工单中已编号的需求条目时（例如 TR 的 SR、issue），规格比它们更细是正常的：条目是评审时点的粒度，规格要细到能写测试。

- 每条 R 标注所属的上游条目，一条可以展开为多条 R。
- 开发中新增、且没有对应上游条目的行为要求，标注"新增"。它影响对外行为时，按项目配置中的方式回报，例如 TR 的基线后变更记录。
- R 与上游条目冲突时，以用户确认的结论为准，并同步回报。

内部算法和模块布局放在技术设计；协议字段、CLI、API 响应等外部契约在这里定义。要求本身可检验，具体测试方法留给技术设计。

区分已确认行为与拟议行为。无法决定的问题放在相关要求附近，说明它阻塞什么，由用户或负责人决定。估计值标注为估计；用条件和可观察结果代替空泛的品质词。

## 交付

保存请求的草案或修订，说明范围、重要变化和仍阻塞的决定。批准状态只来源于明确确认。编写规格不会启动实现。

已有批准且请求继续实现时，把本文件作为依据传递，授权保持有效。需求变更时记录变更原因；未实现的行为保留在规格中并标注状态。
