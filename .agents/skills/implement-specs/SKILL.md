# Implement specs

把已有依据转为经过验证的实现。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。长任务需要跨会话记录状态时，使用 [进度模板](assets/PROGRESS.template.md)，保存在过程区。

## 开始

核对当前任务、已确认的设计、相关项目规则和工作区状态。依据可以是规格、评审文档条目、过程区的任务清单，或已经明确的讨论，文件名以项目为准。重大语义尚未决定时，先完成不依赖它的调查和准备，再给出具体的待决方案。

只读取受影响模块的实现、测试和约束。保留用户已有的修改；需要隔离时使用独立工作区，工作区中的已有内容保持原样。

## 实施与反馈

按可以独立验证的变化推进，复用项目现有的测试和生成工具。修复回归时，能先构造有效的失败用例就先构造。

开发环境无法覆盖的验证：

- 能用日志、模拟、回放或局部验证覆盖的部分，在开发环境完成，并写明覆盖限制。
- 必须在开发环境无法直达的环境中验证的部分，用 `lab-request` 生成需求单，收到回传后再判定结果。

在批准范围内自行决定实现细节和必要修复。发现外部行为、兼容性或模块职责需要改变时，准备修订方案和影响说明，交给用户批准；规格只在批准后更新。

修改类型、协议或依赖后，按项目规定同步生成文件、契约文档和锁文件。事实性同步与语义变更分开处理。

## 验证与结束

执行项目要求的验证，以及与本次变化最相关的验证；风险跨越共享模块时再扩大范围。每次测试注明实际命令、结果和必要环境。修改影响到已有结论时重新验证。

检查最终差异的正确性与范围。复杂差异可以使用 `code-review`。

长期文档与代码同步：行为或设计在实现中发生变化时，在同一提交或 MR 中更新 PRODUCT.md / TECH.md，使它们描述实际交付的内容。完成的任务在过程区的任务清单中更新状态。

完成报告包含实际改动、关键行为的验证结果、未验证的范围与阻塞。提交、推送按已有授权执行；尚未授权时，交付工作区状态与命令结果。
