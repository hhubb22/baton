# Implement Specs — 代码实施与验证

## Goal

在已确认的设计或任务范围内编写高内聚、低耦合的代码，通过自动化测试验证，并保持长期文档与当前系统状态同步。通用红线见 [operating-contract.md](references/operating-contract.md)。

## Workflow

1. **锁定范围与基线**：阅读目标任务、相关规格（`PRODUCT.md` / `TECH.md`）与受影响源码，确认本轮改动的边界。若属于淘汰式重构或上游库替换，先明确列出废弃或删除的旧文件与旧测试列表，严禁将旧资产作为新实现的验收依据。
2. **小步实现与测试（遵循测试金字塔）**：
   - 保持代码简洁直观，只做任务范围内的改动。
   - **优先包内单元测试**：纯逻辑、边界条件、错误分支与存储不变量用快速单元测试或确定性回放验证；全栈多进程或浏览器 E2E 测试只覆盖核心主链路。
   - 运行项目检查命令（见 `AGENTS.md`），确保编译、静态检查与测试全部通过。
   - **三振出局与主动报告**：排错或类型修复过程中，若同类错误连续尝试 3 次仍未解决，禁止继续盲改。立即停下，向用户说明当前错误表现、已排查原因与阻塞点，等待人工确认。
3. **原地同步长期文档**：
   - 若本次改动影响了外部行为、架构或配置，**原地更新** `README.md`、`PRODUCT.md` 或 `TECH.md` 的对应章节。

## Guardrails

- **严禁写工单流水账**：更新 `README.md` 或 `TECH.md` 时，绝不在文档中追加「当前已实现 PS-xxx...」或按工单罗列的历史段落。
- **严禁在生产代码中塞测试环境变量钩子**：不要为了测试异常分支而在业务代码中添加 `os.Getenv("BATON_TEST_*")`；请使用接口依赖注入。
- **不把过程截图或运行日志提交进 Git 仓库**：验证证据写在 PR 描述或工单评论中，不向 `specs/` 提交截图目录。

## Stop Rules

- 完成当前授权任务的代码、测试与文档同步后，汇总改动文件与实际运行的验证命令结果并停下。
