## 概述

Coordinator 内置 Gateway 的行为已于 2026-10-19 获批，实施与验收由 [PS-171](https://linear.app/kakenhe/issue/PS-171) 跟踪。中心只部署 Coordinator 与 PostgreSQL；节点直接连接 Coordinator。R-03、R-04、R-24、R-29、R-38～R-40 规定接入、重启、吊销、流量隔离和升级行为。

员工通过 Baton 查看和管理分布在 Ubuntu 开发服务器、个人 PC 上的 Agent 与 Session。Ubuntu Agent 需要现场信息、设备验收或公网资料时，委托同一员工的 PC Agent，并根据返回的结果继续工作。

北京保存账号、节点绑定、任务与委托的执行记录，并提供统一入口。Agent Session 的完整历史保存在执行节点。Grip 后续作为 Agent 工具接入，Baton 的开发不等待 Grip 完成。

员工还可以为一件长期的事创建 Project。每个 Project 有一个 Project Agent，负责和员工对话、记住项目里的决定、把工作派给各节点上的执行 Agent，并在员工允许的节点上执行命令管理环境。Project Agent 在员工自己的节点上运行，使用节点上已登录的模型订阅；它的对话、记忆和待处理消息保存在北京，因此每次可以在不同节点上运行。所有节点地位相同，不再区分 PC 与 Ubuntu 角色（2026-10-18 修订）。

本期不包含中央设备登记、设备租约、跨员工设备占用检测、危险命令逐条强制审批、实验室无人值守节点。模型访问继续使用各节点已有入口，本期不增加模型 API 代理（提案）。Project Agent 也使用节点上已登录的订阅，北京不做模型推理（2026-10-18 修订）。

## 术语

| 术语 | 含义 |
|---|---|
| 员工 | Baton 中的操作主体，拥有自己的节点、任务与 Session 访问权限 |
| 节点 | 运行 batond、具有稳定节点 ID 的一份运行环境；宿主机与虚拟机可以是不同节点 |
| Gateway | Coordinator 内的节点接入模块，负责已认证连接与受限消息收发，不单独部署 |
| 默认设备 | 员工选定的一个节点：未指定目标的委托发往它，Project Agent 优先在它上面运行（2026-10-18 修订，取代原「PC 执行节点」） |
| Project | 员工的一件长期的事，不绑定代码仓库或节点（2026-10-18 修订） |
| Project Agent | 属于一个 Project 的长期协调角色，按事件在某个节点上运行（2026-10-18 修订） |
| 主对话 | Project Agent 与员工的对话，保存在北京，跨节点保留（2026-10-18 修订） |
| 输入队列 | 北京上等待 Project Agent 处理的消息、任务结果和变更通知（2026-10-18 修订） |
| 事项 | Project Agent 请员工处理的一件事，可以关联一个任务，见 Agent Inbox 行为规格（2026-10-18 修订） |
| Agent Inbox | 列出员工所有待处理事项的界面（2026-10-18 修订） |
| Agent 类型 | Codex、Kiro、Cursor、Pi 等可接入工具；不同类型具有明确的支持能力 |
| Session | 节点上的一次 Agent 会话，保存上下文与历史，可在能力允许时继续使用 |
| 任务 | 一次有明确目标、状态与结果的执行请求；其执行记录保存在北京 |
| 委托 | 从一个任务或 Session 发起、交给另一个节点的任务，保留来源关系 |
| 任务执行记录 | 任务说明、参与者、状态变化、结果摘要及证据引用，不包含完整 Session 历史 |
| Session 历史 | 完整对话、工具调用及其输出等会话过程，保存在节点本地；Project Agent 的主对话不属于 Session 历史 |
| Plane 工单 | 员工管理需求、设计审批和验收的工作项，可关联多次 Baton 任务 |

任务与 Session 分开跟踪：一个 Session 可以先后执行多个任务，任务完成后 Session 可以继续存在。一个任务的子委托可以使用另一节点的 Session。跨节点委托关系不改变本机 Session 的父子关系（提案）。

## 行为

### 身份与节点

**R-01｜员工隔离（原始需求）**

员工只能查看和操作自己的节点、任务、委托、Session、文件、Project 及其对话和记忆。此限制适用于 Web UI、Agent 调用、Project Agent 的工具调用和 Plane 触发的操作。请求引用其他员工的对象时，拒绝操作，不向其节点投递任务。

Plane 集成需要明确的 Baton 员工映射；没有映射的工单事件不能借用其他员工身份执行（提案）。

**R-02｜节点注册与身份（原始需求；流程为提案）**

员工登录后获得有有效期、绑定本人身份的注册凭据，并用其注册 batond。注册成功后，北京保存节点 ID、员工、显示名、系统及注册时间，向节点签发可吊销的连接凭据。节点之间不区分 PC 与 Ubuntu 角色，差异由 R-07 的能力描述（2026-10-18 修订）。

节点重启、显示名变化或网络地址变化不产生新身份。凭据失效时，节点显示认证失败，不反复注册成新节点。虚拟机单独注册；同一身份不能被两个同时运行的环境共用，冲突时显示原因并阻止第二个环境接管身份（提案）。

账号来源、注册凭据的默认有效期及具体操作入口见 D2。

**R-03｜主动连接与状态（原始需求）**

batond 主动建立到北京 Coordinator 的 TLS WebSocket 连接，由内置 Gateway 接入，断线后自动退避重连。部署不要求北京主动访问节点，也不要求节点互相直连。Project Agent 与北京之间的通信也走这条连接（2026-10-19 修订，已批准）。

Web UI 显示在线状态、最后联系时间和状态更新时间。尚未完成状态同步的重连节点不能直接显示为可执行。心跳与离线判定时限必须作为部署配置公开，验证时使用配置值（提案）。

同一 batond 的新连接替换旧连接后，旧连接的迟到断开事件不能把新连接标为离线。连接成功、节点已同步、任务执行状态分别表示，不能互相代替。节点上行只允许访问约定的业务能力；身份取自连接认证，员工与任务归属仍由业务处理器验证（2026-10-19 修订，已批准）。

**R-04｜凭据吊销（原始需求；即时行为为提案）**

员工可以吊销本人节点的连接凭据。吊销生效后，断开该凭据的现有连接，拒绝后续连接和新的中心操作。历史任务记录保留，不能因吊销而删除。

吊销决定保存后即拒绝该凭据的新业务操作；此前已排队但尚未通过业务授权的消息同样受此限制。只有新连接已被禁止且已有连接已关闭，接口与页面才显示已生效；未完成时显示处理中。Coordinator 重启后仍拒绝已吊销凭据。吊销与连接认证、重连并发时也必须满足这些条件（2026-10-19 修订，已批准）。

吊销不等于已经停止离线节点上的 Agent 或外部设备操作。界面须展示这一限制；重新接入需要有效的新凭据。

### 默认设备与目标选择

**R-05｜初始默认设备（已确认原则；选择细节为提案；改为默认设备为2026-10-18 修订）**

员工没有默认设备时，按中心记录的注册顺序，选择最早注册的有效节点。首次自动选择后保存默认值，不因重连、上线顺序或新增节点而重算。默认设备有两个用途：未指定目标的委托发往它（R-06）；Project Agent 优先在它上面运行，它不满足运行条件时 Project Agent 改在其他节点运行，默认值不变（PA-06）。

员工可以在 Web UI 改为本人的其他有效节点。选择离线节点时显示离线提示，仍允许保存。并发修改按中心确认顺序生效，每次响应返回实际保存的节点。

默认节点被吊销或移除时，保留默认值失效的提示，要求员工重新选择，不自动切换到另一个节点。

**R-06｜委托绑定目标（提案）**

委托显式指定本人有效节点时，使用指定节点；未指定时使用默认设备。两者都不存在时，拒绝请求并提示先选择节点。Project Agent 派发任务时总是显式指定目标节点（2026-10-18 修订）。

中心接受委托时固定目标节点。修改默认设备不迁移已有委托。默认设备离线、能力不足或不可用时，不静默改派到另一节点；按排队或拒绝规则处理。

已固定的目标被吊销或不再属于员工时，未启动的任务失败，不改派。已执行任务按可确认的执行事实处理；不能确认结果时进入待核实。

### Agent 与 Session

**R-07｜支持能力可见（原始需求；能力展示为提案）**

节点展示已接入的 Agent 类型、版本和可用能力，包括启动、实时输出、输入、中止、恢复及委托。缺少可执行程序、认证或所需配置时，显示具体缺项。员工可以为节点配置一个默认 Agent，用于未指定类型的委托。

选择不支持的 Agent、系统组合或操作时，在执行前返回不支持原因。新增节点不要求预装所有 Agent。

节点还上报：是否装有 Project Agent Runtime 及其版本、各模型订阅的登录状态（可用、需登录、未知）、员工登记的目录、在这些目录中发现的代码仓库、是否允许 Project Agent 执行命令及使用的 shell。订阅凭据不离开节点（2026-10-18 修订）。

**R-08｜启动与任务关联（原始需求；关联规则为提案）**

员工在 Web UI 选择节点、Agent 类型、工作目录和任务说明后发起执行。接受任务后可查看稳定任务 ID；节点实际启动或绑定 Session 后，记录 Session ID，并在界面建立关联。

启动失败时，任务记录保留失败原因，不创建虚假的运行中 Session。员工可以在节点本地直接使用 Agent；首版只承诺管理 batond 启动或明确接入的 Session，不自动接管任意既有进程。

**R-09｜输入与状态（提案）**

员工可以向支持输入的本人 Session 发送消息。界面区分空闲、执行中、等待输入、已停止和状态未知；等待员工输入不等于任务成功。

在空闲 Session 发起新的执行目标时，按 R-12 和 R-13 创建新任务。对当前任务的补充和答复仍属于该任务，详细内容进入本地 Session 历史；授权变化另行记录到任务执行记录。

一个 Session 一次只执行一个任务。并发提交新任务时，节点确认的首个请求执行，其余请求明确返回忙碌，不隐式排队或混合上下文。同一任务的输入按节点确认顺序处理。不支持输入的接入方式只提供其实际能力。

**R-10｜恢复 Session（原始需求；安全边界为提案）**

节点与 Agent 支持恢复、且本地历史仍在时，员工可以继续已有 Session，并保留原 Session 标识与任务关联。

恢复 Session 不重新执行已提交的任务，也不自动重放历史工具调用。无法恢复时返回原因；若员工选择新建 Session，使用新标识，不伪装成原会话已恢复。

**R-11｜复用与上下文隔离（原始需求；复用规则为提案）**

委托可以创建新 Session 或使用显式指定的本人目标 Session。未指定时默认创建新 Session；只有调用者明确要求，且目标 Session 可接收任务时才复用。

目标 Session 正忙、归属不符或能力不匹配时，返回原因，不擅自中断其中任务或更换上下文。

### 任务与委托契约

**R-12｜请求内容（原始需求；必填规则为提案）**

Web UI 和 Agent 发起的任务使用相同的身份、状态与重试规则。委托请求至少包含以下语义，具体 API 路径与编码由技术设计确定。

| 内容 | 字段 | 约定 |
|---|---|---|
| 请求标识 | `request_id` | 调用方生成的非空字符串，同一次提交重试时保持不变 |
| 任务说明 | `description` | 必填非空文本，说明要完成什么 |
| 来源 | `source_session_id`、`parent_task_id` | 从 Agent 发起时关联来源 Session；属于已有任务时关联来源任务，由平台校验归属；由 Project Agent 发起时关联 Project 和工具调用，由平台填写（2026-10-18 修订） |
| 目标 | `target_node_id` | 可选本人节点 ID；缺省按 R-06 选择 |
| Agent 与 Session | `agent_type`、`target_session_id` | 可选；复用 Session 时采用其 Agent 类型，未指定类型时使用目标默认 Agent，二者都没有时拒绝；显式类型与指定 Session 冲突时拒绝 |
| 工作目录 | `working_directory` | 在目标节点的允许范围内；可使用该节点预先设置的默认目录 |
| 逻辑设备名 | `device_names` | 字符串列表，无设备场景可为空；名称在目标节点解释，平台不据此登记或锁定设备 |
| 授权范围 | `authorization_scope` | 说明允许的操作与限制；设备操作场景必须给出 |
| 期望产物 | `expected_outputs` | 说明需要的结论、证据或文件引用 |
| 排队等待期限 | `queue_timeout_seconds` | 正整数，从中心接受请求时起计算，缺省值见 R-16 |
| 执行期限 | `execution_timeout_seconds` | 正整数，从目标实际开始执行时起计算，缺省值见 R-17 |

缺少必填内容、期限非法或目标已知不支持所需能力时，拒绝请求并指出字段，不启动 Agent。离线节点能力只能依据最后一次上报判断，执行前必须重新校验。

**R-13｜接受与记录（提案）**

“已接受”表示北京已经保存任务及解析后的目标、Agent 和期限，可通过任务 ID 查询；不表示目标已收到或已经执行。响应包含 `task_id`、`request_id`、`target_node_id`、`agent_type`、`status`、排队到期时间与实际执行时限。未能保存时，不投递新任务，不返回已接受。之后修改节点默认 Agent 不改变已接受任务的 Agent 类型。

中心状态未知导致调用超时时，调用方使用原请求标识重试或查询，不自动以新标识再次提交。直接在节点本地运行、未向 Baton 提交的操作不因此获得中心任务记录。

拒绝请求或任务失败时，提供机器可识别的原因和可读说明，区分参数错误、无权限、目标无效、能力不支持、Session 忙碌、请求冲突、等待超时、执行超时、结果格式错误、产物不可用及服务暂时不可用。已经创建任务的错误携带 `task_id`，供调用者查询，不要求重新提交。

**R-14｜委托关系（原始需求；关系规则为提案）**

中心保存来源任务、来源 Session、目标节点和目标 Session 的关系。Web UI 可以从委托方找到执行方，也可以从结果返回来源。

子委托结束后将结果交回原调用方。来源节点离线时，北京保存结果，供恢复后查询或接收通知；来源 Session 已停止时，不为交付结果自动恢复或新建 Session。结果仍可从任务记录查看。

同一委托的重复结果通知不能重复注入来源 Session。无法确认结果是否已交付该 Session 时，单独标出交付待核实，不改变已核实的执行结果，也不自动重复注入。

子委托失败不直接把来源任务标记成功或失败，来源任务可根据结果继续分析。等待中的来源任务不能在仍有未处理委托时自动标为成功。

Project Agent 派发的任务结束后，结果进入该 Project Agent 在北京的输入队列，不要求派发它的那次运行仍在。同一结果只形成一条输入；人工修正产生的新结果版本形成新输入。执行 Agent 再派生的子委托仍按上面的规则交回其来源，不再另外送给 Project Agent（2026-10-18 修订）。

**R-15｜授权边界（原始需求；平台保证范围为提案）**

委托携带员工给出的操作授权，目标 Agent 接收该授权，中心任务记录保存其范围。仅有读取授权的任务不能因委托、恢复或重试被平台改成写入授权。

平台强制执行员工隔离、节点选择与工具入口的权限检查。自然语言授权的理解及具体命令限制依赖 Agent 与工具能力，Baton 不将其宣称为完整的命令沙箱。本期不新增危险命令逐条审批。

Project Agent 只有 Baton 固定的一组工具，后端检查每次调用。它不读写代码。员工在某个节点上开启「允许 Project Agent 执行命令」后，Project Agent 可以在该节点的已登记目录下执行任意命令，用于创建 worktree、检查环境等；开关默认关闭，命令以节点上的员工身份运行，同样没有沙箱（2026-10-18 修订）。

### 等待、状态与结果

**R-16｜排队期限（原始需求；默认值为提案）**

目标离线、尚未完成同步或暂时无法接收时，任务保留为待执行，并显示等待原因。默认排队等待时间为 10 分钟，调用者可以显式设置；界面及接受响应显示实际到期时间。

到期且能确认尚未启动时，任务失败，原因是等待超时；目标之后上线也不能再执行它。节点启动前必须校验任务未过期，不能凭延迟到达的旧投递启动。若投递已经发生但无法确认是否启动，不直接判定“未执行”，按 R-22 核实。

排队期限只约束启动前等待，不作为已经执行的任务失败的依据。

**R-17｜执行期限（提案）**

默认执行期限为 2 小时，调用者可以覆盖；界面与接受响应显示实际采用的值。期限按实际经过时间计算，包含等待输入或子委托的时间，不隐式暂停。执行期限到达时，发起中止并记录超时原因，不重新投递任务。

已确认停止但无法确认操作结果的任务进入待核实。仅在确认没有未核实副作用且执行未成功时，才以执行超时结束为失败。无法联系节点时，不将中止请求显示为已经生效。

**R-18｜任务状态（原始需求；待核实及转换规则为提案，禁止危险重放已确认）**

任务使用以下对外状态，连接状态与状态更新时间单独展示。

| 状态 | `status` 值 | 含义 | 允许的后续状态 |
|---|---|---|---|
| 待执行 | `queued` | 已接受，尚未确认启动 | 执行中、失败、取消、待核实 |
| 执行中 | `running` | 目标确认已启动 | 完成、失败、取消、待核实 |
| 待核实 | `needs_verification` | 是否启动、是否停止或操作结果无法确定 | 执行中、完成、失败、取消 |
| 完成 | `completed` | 结果满足规定结构，执行方明确报告成功 | 无自动转换 |
| 失败 | `failed` | 已确认失败，附原因与可用证据 | 无自动转换 |
| 取消 | `cancelled` | 已确认未执行，或已确认停止且结果已说明 | 无自动转换 |

请求中止是独立标记，不把任务直接改成取消。待核实是需要继续取证或人工处理的状态，不能以清空队列为理由自动改为失败。

结束报告先于启动报告到达时，可以依据同一执行的有效证据补齐中间状态，不丢弃已核实结果。

已结束任务保留后续补充证据和冲突报告，不由迟到消息静默覆盖。人工修正结论需要记录操作者、理由和原结论。

**R-19｜结果内容（原始需求；格式校验为提案）**

任务结果至少包含 `task_id`、`target_node_id`、`session_id`、`status`、`summary`（结论摘要）、`evidence`（关键证据列表）、`artifacts`（产物引用列表）及 `error`（无错误时为空）。尚未建立 Session 时 `session_id` 可为空。证据或产物为空时说明原因。

每个文件引用包含节点或可用存储位置、资源标识和访问状态，不能只返回一条无法判断属于哪台机器的本地路径。原始日志留在节点时，中心保留引用。

Agent 进程退出或输出一句“完成”不足以自动判为成功。执行方未交回约定结构时，记录结果格式错误；若操作结果同时无法确定，进入待核实。Baton 不自行证明结论内容真实，需要人工验收的工单仍由员工验收。

**R-20｜复查与重新执行（提案）**

员工可查看失败或待核实任务的记录与证据，选择继续核实或明确发起新任务。新任务使用新任务 ID，并关联原任务与发起理由。

对可能产生副作用的未核实任务，重新执行前展示原状态，要求员工明确确认；不把“重试查看结果”变成重新执行。人工核实为完成、失败或取消时，记录依据与操作者。

### 取消、重复投递与故障

**R-21｜取消（原始需求；竞态行为为提案）**

员工可以取消本人任务。确认尚未启动的任务取消后，不允许再启动；已投递但无法确认启动情况的请求进入核实流程。

运行中任务收到中止请求后，界面显示请求已发送及确认情况。只有节点确认停止，且操作结果可说明时，才标记取消。停止 Agent 不回滚已经发生的配置修改、文件写入或设备动作。

完成报告先于取消生效时，保留完成结果，并说明取消未生效。重复取消不启动新操作。取消父任务时，同时对其未结束的子委托发起取消；每个子委托独立保留确认状态，不因父任务结束而被标为已停止。

**R-22｜不确定结果（已确认原则；核实行为为提案）**

节点断线、执行进程异常、回执丢失等情形可能使执行事实不确定。平台先尝试查询同一任务的执行状态，不自动重新运行任务或重放其中可能产生副作用的步骤。

能够确认原进程仍在运行时，恢复跟踪同一执行。能够确认最终结果时，补回结果。无法确认时，在等待或执行期限到达后进入待核实；发现执行进程已异常且结果不明时可提前进入待核实。

待核实任务继续接收同一执行的有效证据。因任务记录恢复、Session 恢复或新消息到达而触发的自动流程，都遵守不自动重放的限制。

Project Agent 中途崩溃后，新的运行从主对话里最后一条已保存的内容继续；已经执行过的工具调用不再执行，派发和命令执行以对应任务为准（2026-10-18 修订）。

**R-23｜提交与投递去重（原始需求；幂等边界为提案）**

同一员工使用相同请求标识提交相同内容时，返回原任务；内容不同时返回冲突。重复投递同一任务、重复接收事件或重复返回结果，不启动第二次执行。

节点无法确定某任务是否已经启动时，按 R-22 处理，不能通过新建 Session 来绕开去重。用户显式发起的重新执行按 R-20 创建新任务。Project Agent 派发任务和执行命令时，请求标识由主对话和工具调用确定，跨运行不变（2026-10-18 修订）。

去重记录的保留必须覆盖任务可被重投递的期限。任务记录过期或节点重装后，无法验证的旧投递不得被当作新任务接受；具体保留策略见 D4。

**R-24｜Coordinator 重启与节点恢复（原始需求；连接行为为2026-10-19 已批准修订）**

Coordinator 重启会断开节点连接。batond 自动退避重连并同步状态，同步成功之前节点不可执行。中心恢复时清理旧连接的在线状态，不能把重启前的在线记录直接作为当前可执行状态。

节点上已启动的 Worker 按原有授权与期限继续已有执行，并在本地保存未确认的状态与结果。恢复后补报并核实原执行，不因重连新建执行、重发原任务输入或重复记账。Gateway 不保存离线业务队列；恢复依据中心记录与节点账本。Project Agent 的续租与停止继续遵守 R-25。

**R-25｜中心不可用与本地执行（提案）**

北京短时不可用时，节点上已启动的 Agent 可以继续执行，并在本地保留尚未确认送达的状态与结果。恢复连接后补报，同一结果在中心只形成一份执行记录。

无法持久化中心记录时，不接受或投递新的平台任务。已经交付节点的执行继续按实际情况跟踪；终态消息必须等到中心保存后才算交付成功。

中心不可用期间，节点不能把“已在本地完成”显示为“北京已收到”。本地待补报数据的保留要求见 D4。

Project Agent 的每一步都要先保存到北京。北京不可用时，它无法续租，在本地期限到达前停止，已派出的任务继续执行（2026-10-18 修订）。

**R-26｜batond 异常与重启（提案）**

batond 重启后，保留节点身份和可读取的本地 Session 历史，并尝试确认原 Agent 是否仍存活。进程仍在时恢复跟踪，不能确认时报告状态未知。

batond 重启不自动重建任务执行，不承诺任意 Agent 进程都能跨 batond 崩溃存活。历史文件损坏、被删除或不兼容时，明确显示原因，不能伪造空历史作为恢复成功。

### 数据保存与统一视图

**R-27｜中心任务记录（已确认保存位置；记录字段为提案）**

北京保存任务与委托的说明、发起员工、来源、目标节点、Agent 类型、Session 关联、授权范围、期限、状态变化时间、取消记录、核实记录、最终结果摘要、错误及证据引用。

任务记录在节点离线时仍可查询。界面保留最后一次节点报告的时间，不将过去的执行中状态当成当前在线事实。

北京还保存 Project、Project Agent、主对话、输入队列、项目记忆、事项及其处理记录、浏览器通知订阅，以及 Project Agent 每次运行所在的节点和结束原因（2026-10-18 修订）。

**R-28｜本地 Session 历史（已确认保存位置；访问方式为提案）**

完整 Session 历史由节点保存。北京可以保存 Session ID、所属节点、Agent 类型、关系和最后已知状态，不以任务审计为由默认长期保存完整对话、工具调用与输出副本。

Web UI 请求完整历史时，经权限检查从节点分页或分段取回，每次响应遵守消息上限；整份历史文件的导出遵守 R-32。节点离线时显示暂不可取回；本地数据已删除时显示历史缺失。北京已有的任务记录不因此消失。

Project Agent 的主对话是例外，它保存在北京：员工输入、模型回复、工具调用和工具结果都自动保存，只追加、不删除，所有节点离线时也能查看。压缩只改变发给模型的内容，不改变保存的原文。执行 Agent 不能读取 Project Agent 的对话或项目记忆（2026-10-18 修订）。

**R-29｜实时输出（原始需求；缓存边界为提案）**

员工可以订阅本人 Session 的实时输出。流断开时显示中断，重新连接后可按节点仍保留的历史补取；无法补齐时标出缺口，不把有缺失的输出显示为完整记录。

北京只为当前传输使用有界缓存，不将流经的完整 Session 内容持久化到业务数据库、访问日志或诊断日志。慢客户端不能无限占用内存；限流或丢失时显示原因，并允许从节点重新查看。

任务准备、取消、许可与结果确认优先于 Session 输出。单个节点持续超额输出时，其他节点仍能获得控制消息处理机会，不因共享输出队列满而拒绝其控制消息。单节点与中心总缓冲均有上限；输出超限可丢弃并报告缺口，控制消息不能静默丢失或被虚假确认。慢浏览器不阻塞 Worker 的 Agent 输出读取（2026-10-19 修订，已批准）。

Project Agent 的输出先作为临时片段显示，消息保存后以保存的版本为准；断流后从北京补取（2026-10-18 修订）。

**R-30｜Web UI 查询与干预（原始需求；界面细节为提案）**

员工进入 Web UI 后，可按节点查看 Session 树，也可从任务查看跨节点委托链。Session 展示节点、Agent 类型、状态及更新时间，任务展示执行状态、期限、结果和可操作项。

界面提供发起任务、输入、取消、继续 Session、修改默认设备和查看证据的入口；是否可用由权限、在线状态与接入能力决定。操作失败时显示可定位原因，不以按钮点击成功代替节点操作成功。

Project 界面见 PA-21（2026-10-18 修订）。Agent Inbox、任务结果上的「问 Project Agent」和浏览器通知设置见 [Agent Inbox 行为规格](../agent-inbox/PRODUCT.md)；本期界面只针对桌面浏览器（2026-10-18 修订）。

**R-31｜文件浏览（原始需求；路径与内容限制为提案）**

员工在节点本地配置允许浏览的目录。Web UI 只能列出这些目录中的内容，查看受限大小的文本预览；预览被截断时明确标记。首版文件浏览不包含远程编辑或任意文件上传。

路径规范化、符号链接及 Windows 目录联接后的实际目标仍必须位于允许范围内。越界请求、未授权目录或节点离线时拒绝访问并说明原因。浏览权限不自动扩大 Agent 自身的本地系统权限，也不包含允许 Project Agent 执行命令（2026-10-18 修订）。

完整文件下载、二进制内容和大文件交付遵守 R-32，不能借文件浏览绕过传输限制。

**R-32｜文件引用与大文件通道（原始需求；失败行为为提案）**

固件、抓包、完整日志等文件不经节点控制 WebSocket 传输。控制消息仅携带引用、摘要及受限预览，消息大小与预览上限必须明确配置，并能在超限时返回原因。

任务需要其他节点的文件时，必须通过已配置通道使目标实际可访问。引用不存在、无权限或仅是另一节点的本地路径时，报告产物不可用，不开始依赖该文件的刷机或测试步骤。

首版可使用已有传输通道。若验收包含实际刷机，须先完成固件从 Ubuntu 到 PC 的真实交付；未选通道时不能把该场景标为已支持。

### Plane 集成

**R-33｜工单与任务关联（原始需求；创建规则为提案）**

Plane 工单与 Baton 任务分别保留自己的标识。一个工单可以关联多次设计、开发或验证执行，每次执行保留独立任务记录。

创建工单时只建立关联；进入项目配置的执行触发状态后，才创建任务。触发时必须能确定员工、目标、Agent、任务说明及所需授权，缺项时回写阻塞原因，不尝试猜测。

**R-34｜审批与执行门槛（原始需求；映射规则为提案）**

项目声明需要设计审批的执行，必须在 Plane 记录有效批准后才能触发。批准前可运行显式标为设计准备的任务，不能将其自动升级为已批准的开发执行。

Webhook 只是触发通知，执行前需验证当前工单条件和操作身份。员工直接在 Web UI 发起、不关联 Plane 的任务仍允许执行，并留下发起人和授权记录；本期不将所有本地操作强制纳入审批流。

**R-35｜事件重复、乱序与回写（原始需求；幂等规则为提案）**

Webhook 需要验证来源。相同触发事件只创建一次执行，过期事件不触发已经不满足条件的任务。Baton 自己回写的状态或评论不再次触发同一执行。

Plane 暂时不可用时，Baton 任务记录继续保存，界面显示回写待完成，恢复后补写，不因此重跑 Agent。员工明确发起的新一轮执行可以产生新任务，不能被当作重复事件吞掉。

**R-36｜结果回写与人工验收（原始需求；映射建议为提案）**

每个项目配置实际使用的 Plane 字段与状态，不要求 Plane 状态名与 Baton 枚举相同。采用以下语义映射。

| Baton 事件 | Plane 行为 |
|---|---|
| 执行开始 | 回写进度与 Baton 任务链接 |
| 执行完成 | 写入结果摘要和证据引用；需要最终验收的工单进入待验收 |
| 失败或取消 | 写入原因及已知影响，按项目映射进入相应状态 |
| 待核实 | 明确标出结果未定，不自动进入已验收或完成 |
| 员工验收通过 | 记录验收人、时间和意见，允许工单进入最终完成状态 |
| 员工验收不通过 | 记录意见；新的执行由明确操作触发，不自动重放原任务 |

Agent 报告成功不代表员工已经验收。任务的执行结论与工单的人工验收结论分别保留。

### 安全与运行可见性

**R-37｜敏感数据（原始需求；中心日志边界为提案）**

设备密码及其凭据存储留在员工 PC，不作为委托字段发送北京，也不放入 Agent 上下文、Skill 或报告。Agent 的模型凭据继续由本地运行环境管理，本期不增加中心收集流程。

节点令牌、注册凭据和认证信息不得进入普通业务日志。任务记录只收集执行所需字段，完整 Session 内容按 R-28 和 R-29 处理。Project Agent 使用的订阅凭据留在节点，北京只知道各订阅是否可用；北京保存的 Project Agent 对话不包含凭据（2026-10-18 修订）。任意文本中的敏感信息识别不能作为唯一保护，应避免把秘密写入任务说明或模型输出。

**R-38｜可追溯性（原始需求）**

任务、委托、节点和 Session 具有可关联的标识。状态变更、员工取消、默认设备变更、凭据吊销、人工核实和重新执行记录操作者、时间与关联对象。Project、Project Agent 的每次运行、输入队列条目、事项和它派发的任务也可互相关联；事项的回答、关闭和撤回记录操作者与时间（2026-10-18 修订）。

Coordinator 提供 Gateway 在线节点、连接建立与断开、收发量、队列占用与拒绝次数，以及任务状态分布、排队与执行耗时、待核实数量和回写积压。诊断信息可按节点、连接、消息、任务和执行标识定位，不附带完整 Session 内容或秘密（2026-10-19 修订，已批准）。

**R-39｜容量验证（原始需求；判定方式为提案）**

按约 110 名员工日常使用规划容量，基础估算为约 220 个节点。多 PC 和虚拟机不受“一人两个节点”的固定限制。

保留 PDF 建议的压测场景：500 在线 batond、100 并发委托、100 API 请求/秒、200 节点消息/秒、持续 24 小时，并注入 Coordinator 重启、节点掉线和数据库暂时不可用。

Project Agent 的唤醒、对话写入和输入队列积压另行加入压测，负载在压测前约定（2026-10-18 修订）。

测试前必须约定消息大小、实时输出负载、历史查询量、硬件及延迟、积压和恢复时间的合格阈值。没有这些条件时，只记录观测结果，不声称容量达标。4 vCPU、8 GB 仅是原始部署估算，不是已验证配置。

**R-40｜Gateway 升级兼容（2026-10-19 新增，已批准）**

独立 Relay 合并入 Coordinator 后，原版 batond 使用原有节点身份、凭据、账本和协议，仅调整连接地址即可接入。任务提交、取消、结果交付、文件浏览、Session 历史、实时输出、补充输入与恢复沿用原有权限和确认规则。补充输入的确认丢失后查询原操作，不自动重发正文。

中心按单个活动 Coordinator 部署，允许升级期间节点短时断线，按 R-24 恢复。Gateway 与业务处理共享进程，进程故障会同时影响两者。多副本调度、iroh 接入和节点之间直接派发不属于本次重构范围。

## 验收场景

以下场景用于确认行为是否可观察，具体测试工具与环境留给技术设计。

| 场景 | 条件与操作 | 可观察结果 | 关联要求 |
|---|---|---|---|
| 三类 PC 接入 | 在 Windows、macOS、Linux 的约定版本上注册与重连 | 各节点身份稳定、能力准确，虚拟机可独立展示 | R-02、R-03、R-07 |
| Ubuntu 委托 PC | 本人节点在线，执行一次现场调查或公网资料查询 | 委托关系可追踪，返回结构化结果，北京有记录，完整历史在节点 | R-12～R-19、R-27～R-30 |
| 多节点 | 新增节点、修改默认值、显式指定目标 | 默认值稳定，已有委托不迁移，目标不可用时不静默改派 | R-05、R-06 |
| 离线等待 | 默认设备离线且任务未启动，等待到期后再上线 | 到期任务失败，节点不补执行 | R-16、R-23 |
| 重复提交 | 重复提交相同请求，重复投递和重复返回结果 | 只有一条任务执行，冲突内容被拒绝 | R-13、R-23 |
| 结果丢失 | 操作已发出后中断连接，使执行事实无法确认 | 查询原执行，必要时待核实，没有自动重放 | R-18、R-20、R-22 |
| 取消竞态 | 分别在未启动、运行中、完成前后取消 | 状态符合实际确认，未宣称回滚，子委托单独可追踪 | R-18、R-21 |
| 中心故障 | 重启 Coordinator，短时停止数据库服务 | 节点退避重连，同步前不可执行；原 Worker 不重复启动，补报可重试且中心幂等记账 | R-24～R-26 |
| 吊销竞争 | 吊销与认证、重连、已排队消息同时发生，随后重启中心 | 已吊销凭据不能继续取得业务授权；新连接不能被旧连接退出事件误标离线 | R-03、R-04 |
| 输出洪泛 | 节点 A 持续超额输出，节点 B 同时接收任务与取消；浏览器慢读 | B 的控制消息持续得到处理，缓冲有界，输出缺口可见，Worker 读取不中断 | R-29、R-38 |
| 接入升级 | 原版 batond 保留原身份与账本，连接到新 Coordinator | 不重新注册；任务、浏览、输入与恢复行为兼容 | R-40 |
| 数据位置 | 执行并查看 Session 后使节点离线 | 中心仍可查任务记录，完整本地历史明确不可取回，中心无默认历史归档 | R-27～R-29 |
| 越权与越界 | 请求其他员工对象或通过链接访问允许目录外文件 | 操作被拒绝，无跨员工执行或目录外内容返回 | R-01、R-31 |
| Plane 全过程 | 触发一次需审批的执行，重复事件，再回写结果并人工验收 | 审批门槛有效、只执行一次、成功与验收分开 | R-33～R-36 |
| 产物不可用 | 委托引用目标无法访问的固件 | 明确失败或阻塞，不执行依赖该文件的步骤，不借控制连接传输文件 | R-32 |
| Project Agent | 见 Project Agent 行为规格的验收表 PA-A01～PA-A12 | 跨节点接续、无重复派发、离线等待、命令执行 | R-14、R-15、R-22、R-27～R-29（2026-10-18 修订） |
