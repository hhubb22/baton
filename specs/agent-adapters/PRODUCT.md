# Agent 适配与扩展行为规格

Status: draft
Basis: 已确认的 Agent 接入范围；t3code fork 的完整 provider adapter；配套 [技术设计](TECH.md)。

Thread 创建、持久恢复和审批使用上游执行模式，设备按模式报告可用性。验证范围以本地替身和离线回放为准，不代表各系统原生沙箱均已验证。记忆停用与恢复由 [Project 长期记忆规格](../project-memory/PRODUCT.md)定义。

## 概述与范围

员工和 Project Agent 通过现有 Thread 功能使用 Pi、Codex、Kiro、Cursor、Grok 和 Antigravity。Agent 接入使用 t3code fork 的 provider，沿用各 Agent 的原生会话、认证和模型，提供新建、排队、停止和恢复；插入和换模型按上游报告的能力提供。协议层的重试、重连、插入归属和回合结束判断以上游实现为准，Baton 负责持久接收、不重发未知输入和停止回收。

| Agent | 本期工作 |
|---|---|
| Pi、Codex、Cursor | 通过 t3code 的完整 provider 与节点 agent-host 接入 |
| Kiro | 已接入 fork 的 ACP provider 与节点 agent-host；程序已安装且认证为 valid 或 unknown 时开放网页新建与恢复，版本和系统不设白名单 |
| Grok、Antigravity | 切换后接入，使用设备上已经安装、配置并完成认证的原生程序 |

Claude、OpenCode、Muse、通用 ACP Agent 目录接入均不在本期。Project Agent 的一次性命令由独立 Execution 运行。原生 fork、rollback、计划卡片、独立子 Agent 界面、自动续跑、多账号选择，以及 Agent 安装更新和登录托管均不在本期。

本文补充 [Baton 行为规格](../baton/PRODUCT.md) R-06 至 R-16、R-21、R-25 和 D1。Thread 状态、员工隔离、设备目录限制、归档和附件约定继续适用。本期 Thread 历史统一使用中心保存的记录，补齐不可用原因到网页和 Project Agent 的传递，并将设备接收命令与 Agent 启动、输入准备及发送分开确认。

## 行为

### R-01｜接入与可用性

设备分别报告各 Agent 的版本、模型、可用状态、操作能力及诊断原因。网页与 Project Agent 读取中心保存的同一份设备报告；原因在节点上报、中心保存和查询中保留，缺少程序、运行依赖、认证或配置时显示具体缺项。只有状态为可用且明确支持新建的 Agent 才能选择创建，未验证也属于不可创建状态。

四个 Agent 在程序或 SDK 已安装、认证有效或 unknown 时报告可用，按上游 adapter 与已实现的执行路径开放能力。版本未知、版本探测失败或超时、系统组合缺少验证证据只记录到诊断，不阻止新建。缺程序或明确缺少认证时报告不可用；整次探测无法确认安装时报告未验证。Cursor 保留公共安装完整性检查，原生 sandbox 的明确失败仅影响需要该沙箱的执行模式，按 R-11 报告；公共运行依赖或认证明确失败影响整个 Agent。诊断原因变化后，消费端能读取到更新后的原因。原因只包含有限长度的脱敏摘要，不携带凭据或原始诊断输出。创建前再次检查执行条件；检查失败时返回原因，不切换 Agent、账号或设备。新接入 Agent 的交付验证必须覆盖发送、停止及恢复，单次对话成功不能代替这些验证。

### R-02｜探测与准备

后台版本和可用性检查使用上游 driver 的检查；Kiro 另在上游 status 之外执行 `kiro-cli --version`。探测不发送 prompt，不调用 authenticate/login 或打开登录浏览器，只使用临时工作目录，不连接员工正在执行的会话。Kiro 的完整探测仍通过上游建立空的发现会话，读取能力与模型。

安装状态无法确认时报告未验证并说明缺项。四个 Agent 的认证状态未知时均允许创建，reason 提示首次执行由原生程序检查；明确认证缺失时拒绝。认证与模型目录分别判断：缓存目录或公开模型列表不能证明账号有效；通过认证准入但模型目录读取失败时，允许使用原生默认模型，并显示相应原因。

员工修复本机安装、认证或配置后，重启 batond 会重新探测。探测建立的进程、会话临时数据和后台任务有明确期限并被回收；探测失败不影响既有 Thread 的执行。

Cursor 缺少随设备分发的运行依赖时显示安装不完整；设备使用时不临时联网安装依赖。Grok、Antigravity 缺少原生运行环境时提供本机配置指引。

Kiro 的独立版本命令限时 4 秒，stdout/stderr 各最多收集 4096 字节，只返回版本号，诊断不外传。程序已安装且认证为有效或 `unknown` 时，节点报告 `available`、`create: true`、`resume: true`，网页开放新建与恢复。reason 记录版本、系统、认证未知和版本探测问题。系统或版本（含预发布、构建后缀）、版本超时或不可解析不限制创建；缺程序或明确认证 `missing` 为 `unavailable`；不满足准入条件的新建请求返回 HTTP 422、`agent_unavailable`。本地 CLI 的 `open --agent cursor|pi|codex|kiro` 支持四个 Agent，默认 Cursor。Kiro 2.32.0 的离线回放和注入已验证 capability 的 e2e 验证自动化行为，不能证明真实账号授权有效。

### R-03｜认证与会话归属

每台设备上的每种 Agent 使用一份本机认证上下文。本期不提供网页多账号切换。Thread 记录所用 Agent、原生会话和认证配置位置的关联；恢复只能使用这份关联。

执行 Agent 的凭据与 Project Agent 模型订阅分别管理。`batond login openai-codex|xai` 的成功不代表 Codex 或 Grok Thread 已可用。凭据不进入中心、消息正文、历史或诊断日志。

Kiro 从 PATH 查找 `kiro-cli`，沿用设备用户的原生认证配置；节点不提供 `BATON_KIRO_*` 或 `KIRO_HOME` 配置入口，profile 关联保存用户主目录 `homedir()`。

认证失效、配置位置变化或账号不能访问原会话时，停止创建或恢复并说明原因，不能新建空会话来冒充恢复。Kiro 实际回合中发生明确认证失败时，向 Thread 返回固定文案“Sign in to Kiro CLI and try again.”；其他 provider 错误返回“Check Kiro CLI on this device and try again.”。Baton 不自动登录、不透传原始错误、不重发输入。

### R-04｜新建与恢复

设备持久接收新建或恢复命令后及时返回接收确认，原生 Agent 的慢启动异步完成。已接收命令不表示 Agent 已就绪；只有完成原生会话建立和归属保存后，才显示 Thread 已打开或恢复成功。恢复进行中的状态保持到实际成功、失败或取消，接收确认不会清除它；期间重复恢复请求复用同一操作。启动失败通过后续状态报告显示原因，接收确认丢失后用同一命令标识重试，不重复创建或恢复。

首次启动完成前收到停止时，取消该次打开并清理迟到创建的运行实例，不再报告打开成功；若打开成功已确认，则按已打开会话停止。最终结果在进程重启后保持一致，不能重新执行已经取消的打开。

首次创建 Thread 时，原生会话归属必须先保存，再发送第一条消息。恢复时核对原生会话与工作目录，Thread ID 保持不变，历史中的工具调用不再次执行。

Kiro 的恢复与发送核对从打开 adapter 起就指定既有原生会话，先以 `session/list` 核对会话 ID 与 cwd，再 `session/load`；缺失或 load 失败时明确失败，整个路径不创建替代会话。

原生会话或本地映射缺失、历史不匹配时，返回历史缺失或不可用原因。网页仍能查看中心已经保存的回复；员工可以自行新建 Thread。

### R-05｜输入与重复确认

设备将消息持久保存到队列后返回接收确认，不等待 Agent 接收。排队由 Baton 保存；Agent 结束当前一轮后才发送下一条。只有 Agent 接受该输入后才显示已发送，本地队列已保存与 Agent 已接收分别表示。Agent 启动和提交期间，停止请求及状态查询仍能被处理。

消息发送过程中断线、超时或进程退出后，先查原生会话记录。能确认输入存在时记录已发送；不能确认时显示状态未知，Baton 不自动再次提交同一条消息。Agent 协议层自身的重试与重连沿用上游行为。

### R-06｜插入

插入只在 Agent 报告支持时提供，归属判断以上游实现为准；不支持插入的 Agent 执行中只提供排队。Kiro 不支持插入。需要改变方向时，员工先停止当前一轮再发送新消息。插入结果无法确认时显示状态未知。

### R-07｜模型

模型列表和标识来自实际 Agent。未指定模型时使用该认证上下文的默认模型；界面里的“默认”不能作为虚构模型标识发送。Kiro 的模型取 Thread `model`、`adapter_config.model` 或 `default`；`default` 在原生 `session/new` 中省略，具体 ID 经 `_meta.kiro.modelId` 传递，整个 Thread 固定该选择，不支持轮间换模型。

Pi、Codex、Cursor 开放 `switch_model`，排队消息可为新一轮指定模型，同一个 Thread 保留原生会话身份。省略模型时沿用最近确认提交的回合模型，首次使用创建配置；插入消息沿用活动回合模型，不接受显式模型。Kiro 的 fork adapter 不支持换模型，整个 Thread 使用创建时的选择。Pi 的 `set_model` 明确拒绝和 Cursor SDK 明确报告模型不可用时，能够确认输入尚未提交，Worker 持久撤回该条消息并显示原因，继续处理后续排队消息。超时、断连、Codex 提交错误和其他不能证明未提交的失败按 R-05 处理；显式恢复使用最近确认提交的回合模型，只读取原生证据，不重发旧输入。

### R-08｜停止

停止覆盖当前一轮及其在本机启动、由该会话拥有的工具和后台任务，并撤回尚未发送的排队消息。取消请求的响应表示请求已处理；设备继续回收执行实例与所属进程，全部确认后显示已停止，下一条消息或显式恢复可继续原会话。回收或输入结果无法确认时显示状态未知。

发送后立即停止、长工具运行中停止和子任务运行中停止都必须生效。原生取消未在一分钟内完成时，结束该 Thread 的 Agent 进程树；不能误杀其他 Thread。无法确认回收结果时显示状态未知。停止不撤销已经发生的文件修改或其他动作。

### R-09｜回复与回合归属

只把当前 Thread、本轮执行的回复写入其时间线，按接收顺序保存。回合何时结束、子任务和后台任务如何归属以上游 adapter 的事件为准；恢复过程重放的旧消息不能当作新回复再次上报。

上游明确报告模型拒绝、认证失败、限流或 provider 错误等回合失败时，该回合以失败结束并保存安全原因。触发输入保持已发送，不自动重发；原生会话与进程保留，后续排队消息照常执行，没有排队消息时 Thread 回到空闲。网页在该回合显示失败和原因。运行时请求无法应答、事件流断开、发送结果无法确认、host 崩溃或连接丢失仍显示状态未知。

一轮结束前保存已经收到的回复。迟到的旧回合事件不能混入下一轮。本期不启用会在没有 Baton 输入时自动启动新一轮的原生功能。

### R-10｜历史与实时输出

Thread 历史是中心保存的输入和回复记录，所有 Agent 格式相同。网页与 Project Agent 读取同一份记录并按序分页，浏览器不解释各 Agent 的原始协议，历史读取不依赖设备在线或执行进程存活。

在 Baton 之外继续同一原生会话产生的消息不出现在历史中。正文、容量和分页预算沿用主规格 R-15、R-16。实时输出发生截断或丢失时标记缺口。工具过程留在设备上。

### R-11｜本机权限与后台运行

Thread 创建时直接选择上游 `RuntimeMode`，网页、本地 CLI 与 Project Agent 使用相同的值、默认值和 adapter 语义。默认值引用上游 `DEFAULT_RUNTIME_MODE`，当前为 `full-access`。创建后所有回合、换模型、Worker 重启与原生会话恢复沿用已保存模式；详情可以查看，本期不提供运行中切换入口。

| 上游模式 | 上游显示名称 | 行为 |
|---|---|---|
| `approval-required` | Supervised | 按 provider 的原生策略，在需要批准的操作前等待用户决定 |
| `auto-accept-edits` | Auto-accept edits | 按 provider 策略自动接受编辑，其他需批准的操作等待用户 |
| `auto` | Auto | 支持的 provider 自动审查常规操作；其他 provider 按上游处理，可能仍需用户批准 |
| `full-access` | Full access | 按 provider 的 Full access 策略执行工具，原生用户规则或 provider 检查仍可能要求确认 |

各 Agent 的可选模式沿用上游明确声明的支持范围和实际 driver 行为。上游没有缩窄支持范围时，沿用公共模式契约。内部 shell 仍只由 `nodes.exec` 创建，以设备用户权限运行，不增加模式选择。

模式表达上游的审批与执行策略，具体文件隔离、网络访问与自动审查按 provider 实际实现。Pi、Kiro 的非 Full access 模式可以提供审批行为，但不因此具有系统沙箱。Cursor 在 Windows 上的审批与文件隔离也按 SDK 的真实能力说明，界面不能把所有非 Full access 模式统一标成 Sandbox。

设备报告上游模式列表、每个模式的可用性和原因，以及上游默认值；网页与 Project Agent 使用同一份报告。明确属于某个模式的原生 sandbox 故障只影响依赖该沙箱的模式，公共依赖或认证失败影响整个 Agent。默认模式明确不可用时，省略模式的创建返回原因，不自动改选其他模式。缺少某系统或版本的验证证据不新增白名单限制。

网页在新建位置、Agent 或设备变化后刷新模式，保持上游名称及语义。已选模式变为不可用时保留选择并显示原因，用户重新选择后提交。新建区与详情说明 Full access 可以按设备用户权限访问目录外文件和网络，实际能力继续受原生程序与操作系统限制。

中心创建时保存实际模式，离线等待不改变它；设备在实际执行前核对模式与运行条件。新建请求的幂等内容包含模式，同一标识重试保持原结果，改变模式返回冲突。已有 Thread 不因上游默认值、报告或配置变化而改变模式；不支持或不可用时明确失败，保留原选择与历史，不切换权限后继续。

Full access 继续受员工隔离、设备归属和 Thread 初始工作目录检查约束，文件浏览 API 仍受授权目录限制。设备上的「允许 Project Agent 执行命令」只控制 `nodes.exec`。Project Agent 省略模式时采用上游默认值，可以按用户要求选择其他支持模式，不能因执行失败自行改变用户选定的模式。

adapter 已按原生策略自动处理的操作继续沿用上游。上游实际发出的待审批请求必须交给员工处理，保留其原因、可选决策与作用范围；Baton 不把待审批请求统一改成自动允许，也不代替上游做另一套命令审查。Full access 下仍发出的用户规则或 provider 检查请求同样等待员工决定。等待计入原回合时限，停止后到达的请求取消。

普通提问、权限审批和 MCP elicitation 复用 Thread 的持久问题与回答流程，按上游请求类型展示。刷新后可以继续回答，离线回答仅交给恢复连接后仍在等待的原请求；原生请求已结束或不可恢复时明确关闭。回答结果不确定时保留记录，不自动重发。审批等待属于 Thread，本期不另触发 Project Agent 代替员工批准。

### R-12｜交付与升级

按操作系统记录已验证的 Agent、版本和能力组合，缺少验证证据不阻止创建。程序、认证和依赖检查沿用上游 driver 与本机探测结果，Baton 不另设系统或版本白名单；版本探测失败或超时只记入诊断。只有明确的数据丢失、越权或重复副作用风险才进一步限制能力。

设备安装包、Node 运行依赖和原生 Agent 程序分别报告缺项。更新后使用当前安装版本重新检查；原生会话映射不匹配时明确失败。实验室阶段沿用主规格 R-25，不维护旧开发版本的数据读取分支。

## 待确认与验证事项

| 项目 | 缺少的证据 | 阻塞范围 |
|---|---|---|
| Cursor 认证 | 使用设备显式配置的 `CURSOR_API_KEY`，不读取 ambient 账号或 keyring | 按本机安装、依赖与认证结果开放 |
| Kiro | 离线夹具与本地替身验证自动化行为，真实账号授权由原生程序在实际执行时检查 | 程序已安装且认证 valid/unknown 时开放新建与恢复，版本和系统不限；上游不支持 steer 和换模型 |
